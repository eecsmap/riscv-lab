# 第 4 步：中断

目标：核接受三根外部中断线（软件 MSI、定时器 MTI、外部 MEI），在**架构边界**上、而且只在架构边界上接受它们，
记录现场、进处理程序、`mret` 回到那条还没执行的指令。做完这一步，MCU-0 的闪灯固件可以从轮询改成 `wfi` 睡眠加定时器中断。

唯一的新机制：**中断只在 S_IF_REQ 采样。** 那一拍前一条指令的所有写入已经在 S_ARCH 落地，下一条指令还没有向总线发出任何东西，
所以没有任何东西需要取消或重做，`mepc` 就是 `pc`。

## 做什么

| 组 | 内容 |
| --- | --- |
| CSR | `mie`（0x304）：bit 3 MSIE、bit 7 MTIE、bit 11 MEIE 可写，其余读 0。`mip`（0x344）：同样三位，直接反映三根中断线的电平；**写 `mip` 合法但不改变任何东西** |
| 判定 | 挂起 = `mip & mie`；可接受 = `mstatus.MIE && 挂起非零`；优先级 MEI > MSI > MTI |
| 接受 | 在 S_IF_REQ，**先于**取指地址检查：cause = `{1, 0…, 11/3/7}`，tval = 0，epc = `pc`，`trap_interrupt` = 1，进 S_TRAP，不发取指请求 |
| `wfi` | 0x10500073，合法的空操作，退休一次。不睡眠，也不会让一个被屏蔽的中断变得可接受 |
| 观测 | `dbg_irq_enabled`、`dbg_redirect` 两根观测线必须实现，注入器靠它们定位（见 TODO 6） |
| 变异开关 | `EARLY_IRQ`、`STALE_MIE`、`IRQ_BAD_MEPC`，见下 |

## 中断从哪来

harness 有一个测试用的"中断控制器"：一个注入器在你指定的**微架构时刻**拉高某根线（`IRQ_POINT`、`IRQ_LINE`），线一直保持高，
直到处理程序往 `0x6000_0000` 写一次把它安静下来。核里没有任何"粘住的挂起位"：电平就是挂起。共享处理程序
`tests/cpu/tests2/ihandler.S` 负责记录 cause、计数、安静中断源。测试程序可以往 `0x6000_0008` 写 1 来**布防**：
之后的下一次指定时刻才注入，避免启动代码抢走那一次。

| `IRQ_POINT` | 时刻 | 核此时的状态 |
| --- | --- | --- |
| 1 | 取指请求挂着、ready 还没来 | S_IF_WAIT |
| 2 | 取指已握手、响应还没回来 | S_IF_WAIT |
| 3 | 数据请求挂着、ready 还没来 | S_MEM_WAIT |
| 4 | 数据已握手、响应还没回来 | S_MEM_WAIT |
| 5 | 写回调度的那一拍 | S_WB |
| 6 | 一条跳转、分支或 mret 正在写回 | S_WB，`dbg_redirect` 为 1 |
| 7 | 写入落地的那一拍 | S_ARCH |

无论注入在哪个时刻，正确的核都只在下一次 S_IF_REQ 接受它；在途的取指、访存都正常完成，那条指令照常退休。

## 测试

```sh
make step4            # 20 次运行
make step4-mutants    # 5 个检查
```

还没动手时，第 3 步的核在 i01 就会超时：`mie` 还是未知地址，程序进不了中断。这是起点，不是 bench 的问题。

| 测试 | 查什么 |
| --- | --- |
| i01 ×2 | 一个定时器中断：cause 带中断位，返回后 `mip` 为 0，不再有第二个；另跑一次随机时序 |
| i02 | 三根线同时拉高，接受顺序必须是外部、软件、定时器 |
| i03 | `mstatus.MIE` 关、或 `mie` 关时，一直挂着的电平都不能被接受；打开后立刻接受 |
| i04 | `mip` 只是电平的窗口：写它合法，但既不能凭空产生、也不能清掉挂起位（第 4 步版本，`-DHAS_S` 时期望不同） |
| i05 | `wfi` 退休恰好一次，使能关时只是继续往下执行 |
| i06 | `mret` 恢复使能时中断源还挂着，必须立刻再次进入，三次，`mepc` 都相同 |
| i07 | 在一条被采纳的回跳分支写回时注入：`mepc` 必须是**跳转目标** |
| i08 | 中断注入在一条会出总线错误的 load 的响应期间：load 的访问错误先报，中断其后 |
| i09 ×3 | 中断落在 store 的请求期、响应期、慢总线：读回的值正确，恰好一次中断 |
| j01 ×6 | 使能确认生效后布防，中断分别落在目标 load 的六个时刻；load 完成并退休，`mepc` 恰好是下一条 |
| j02 ×2 | 50 次读加写同一地址，**在总线上计数**：req 102、写请求 51、实际写入 51；快总线和慢总线各一次 |

每次运行除了程序自己的检查，还核对日志里的注入上下文：时刻真的出现过（`hits > 0`）、线拉高一次、被安静的次数、
触发时的状态和 pc（`fire_pc=@target_insn@` 这种写法会被换成标签的实际地址）、使能是否真的生效。
**一个只看"中断最后被处理了"的测试，会让在错误时刻接受中断的核蒙混过关。**

## 杀死矩阵

| 变异体 | 含义 | 被谁杀死 |
| --- | --- | --- |
| `STALE_MIE` | 在 S_ARCH 就采样，用的是还没落地的 MIE | 除 i04 外全部。进 trap 时 MIE 的清零还没落地，同一个中断在处理程序第一条指令前再进一次，`mepc` 被覆盖成处理程序地址，之后一路非法指令（i01 日志里两个中断只隔 2 拍） |
| `IRQ_BAD_MEPC` | 中断的 `mepc` 记成上一条指令 | i07、i08、j01 六个时刻 |
| `EARLY_IRQ` | 也在 S_MEM_WAIT 接受，放弃已经发出的访存 | j01 取指和访存请求期（撤回请求、`mepc` 错）；**j02 慢总线**（store 被执行两次） |
| `DUP_STORE`（harness 的对照） | 内存模型把一个被监视的写执行两次 | 只有 j02 的 `writes` 计数 |

`EARLY_IRQ` 在 i09 里**活了下来**：store 被中断吞掉后，处理程序返回到它，它又执行一遍，写的是同一个值，程序看不出来。
只有在总线上数请求和实际写入的 j02 能抓住它。这是这一步最值得记住的一课：**"最终值对"不等于"恰好一次"。**

## 常见的坑

- 在 S_IF_REQ 里先做了取指地址检查或发了请求，再看中断：中断必须最先判定，而且判定为接受时不能发请求。
- `trap_interrupt` 没有在下一次同步异常时清零：程序不受影响（`mcause` 来自 `trap_cause`），但日志里同步异常的 TRAP 行也会带 `(interrupt)`，调试时会误导你。
- `mip` 写成可写：i04 code 3。
- `wfi` 没加进合法指令：i05 一进去就是非法指令 trap。
- `dbg_irq_enabled` 一直是 0：j01 的注入器永远不会触发，WAIT_IRQ 超时报 code 5。
- `dbg_redirect` 一直是 0：i07 等不到注入，循环跑完报 code 1（或先撞上周期上限）。
- 日志里两个中断只隔几拍，第二个的 epc 是处理程序地址：中断在 S_IF_REQ 以外的地方被判定了，对照 `STALE_MIE`。
