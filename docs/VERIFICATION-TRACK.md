# 测试轨道：如何实施专业的验证

分支 `teach-verify`，2026-10-10 起草。这是和 `docs/TEACHING-PLAN.md` 平行的第二条轨道：实现轨道教学生写核，
这条轨道教学生**证明核是对的**，用的是同一个 harness、同一个核、同一批测试。每个模块都锚定在仓库里一件
真实存在的测试设施上，并且附带一次它所对应的真实事故：这些纪律没有一条是凭空规定的。

## 贯穿全程的四条原则

1. **一个不会失败的测试什么都没证明。** 每写一个测试，先说出哪个缺陷会让它失败，再用变异体证明它确实会失败。
2. **答案对不等于核对。** 协议、时序、观测口都要独立检查；一个违约的核也能算出正确答案。
3. **期望值要推导，不要手数。** 从反汇编、从生成器、从参考实现得到期望，手数的数字只能作为交叉对照。
4. **测试工具自己也要被测试。** 运行脚本、检查器、生成器各有自己的变异体和自测。

## 模块

每个模块四栏：学什么、读仓库里哪个东西、动手做什么、怎么算过。"配合步骤"指实现轨道里的第几步之后做。

### V0 不会失败的测试（配合第 1 步之前）

- **学什么**：测试为什么会骗人。六种真实形态：失效的命令行选项让检查空过；崩溃被当成拒绝；管道吞掉退出码；
  子串误匹配；测的是复制品而不是本体；夹具恰好绕开了它要防的 bug。
- **读什么**：流水线 P1 报告 §3.6 "Checks that could not fail"：`CHECK_EQ` 把常量装进 `t6` 再和 `t6` 比，
  比较的是寄存器自己；以及 2026-09-25 的六例记录。
- **做什么**：给 `s1_tohost` 写一个"永远通过"的检查，把它交给一个故意算错的核，看它变绿。然后改到它会红。
- **怎么算过**：交出的每个检查旁边写着"哪个变异体杀死它"。

### V1 协议监视器（配合第 1 步）

- **学什么**：接口契约怎么变成可执行的检查。`tcpu_harness.v` 里七条规则：撤回、payload 变化、双发、无请求的响应、
  同拍响应、读带写负载、commit 与 trap 同拍。
- **读什么**：harness 第 580 到 635 行；`MEM_SAME_CYCLE`、`REQ_WITHDRAW`、`LOAD_WDATA_LEAK` 三个参数，
  它们是**监视器的自测**：故意让一方违约，监视器必须报。
- **做什么**：新增第八条规则，例如"写请求的 `wmask` 必须落在 `size` 允许的通道内"，再写一个触发它的核变异体。
- **怎么算过**：规则在正确核上静默，在变异体上恰好报那一条；`make step1-mutants` 多出一行 ok。

### V2 观测口与交叉检查（配合第 1 步）

- **学什么**：为什么 commit 端口报的值要在下一拍从寄存器堆里真的读一次（`OBS ERROR`）。"一条只靠观测端口
  就能产生的通过轨迹"是不被接受的。
- **读什么**：harness 的 `dbg_ra` 回读路径；`TeachingCpuObs` 的稳定契约注释。
- **做什么**：让 commit 端口说谎（报 `wb_value + 1`），确认被抓；再让寄存器堆写错而 commit 报对，确认也被抓。
- **怎么算过**：两种谎言各被一条 OBS ERROR 指出，日志能说出寄存器号和两个值。

### V3 变异测试纪律（配合第 2、3 步）

- **学什么**：故障注入参数是**受控缺陷**，一个参数一个真实 bug。测试集的质量用"杀死矩阵"衡量：每个变异体
  至少被一个测试杀死，活下来的变异体就是缺的测试。
- **读什么**：`tcpu_core.v` 的 28 个 `FAULT_*` 参数及其注释；M2 报告里的变异体表；`tests/cpu/tests` 的 d 系列
  每个都对应一条审查意见。
- **做什么**：为第 2 步的 t01 到 t03 建杀死矩阵（`X0_WRITABLE`、`NO_LOAD_SEXT` 起步），然后自己加一个新变异体
  并补上杀死它的测试。
- **怎么算过**：矩阵里没有空行，也没有空列。

### V4 时序剖面与随机化（配合第 2 步）

- **学什么**：同一个程序在不同存储器时序下跑：立即应答、固定延迟、随机延迟、同拍应答。只在一种时序下通过的核
  不算通过。P1 的随机差分抓到了定向测试漏掉的 bug。
- **读什么**：harness 的 `READY_DELAY`、`RESP_DELAY`、`RANDOM`、`SEED`；`teaching/Makefile` 的三个 tag。
- **做什么**：构造一个只在 `RESP_DELAY > 1` 时才错的核 bug（晚一拍采样 `resp_rdata`），证明 plain 过、slow 不过。
- **怎么算过**：这个 bug 在三种剖面中至少被一种杀死，并且写明是哪一种、为什么。

### V5 期望值从哪里来（配合第 2、3 步）

- **学什么**：`perf06_iws` 的退休数 70001 和 65729 是脚本从反汇编数出来的，不是手算的；`check_retirement.py`
  还确认汇编器没有把跳转松弛成别的指令序列。
- **读什么**：`experiments/IPS-campaign/workloads/check_retirement.py`；`ROI-POLICY.md` 的"窗口边界"。
- **做什么**：写一个脚本，从 `objdump` 推导 `s1_tohost` 应退休的指令数和每条的 rd 值，和日志里的 COMMIT 行逐条比。
- **怎么算过**：脚本对参考核和学生核都给出一致判定；把测试程序改一条指令，脚本的期望自动跟着变。

### V6 微架构时刻注入与覆盖率（配合第 4 步）

- **学什么**：中断不是"随便某个时刻"来的。harness 把中断线精确拉在 12 个微架构时刻上（`IRQ_POINT`），
  `irq_hits` 记录那个时刻到底出现过几次，"一次运行不能声称它没有的覆盖"。
- **读什么**：harness 的 `irq_moment` 定义和 `fire_*` 上下文锁存；i 系列和 j 系列测试。
- **做什么**：加第 13 个注入点（例如"store 的响应回来的那一拍"），写测试，证明 `irq_hits > 0`。
- **怎么算过**：新注入点有命中计数，`EARLY_IRQ` 这类变异体在它上面仍被杀死。

### V7 差分验证（配合第 2 步起随时）

- **学什么**：两个实现跑同一个程序，比 commit 流。P1 用 40 个生成的 hazard 程序做架构差分，
  "每个测试缺陷在两边表现为同一个错误结果，这就是它们和核 bug 区分开的方法"。
- **读什么**：P1 报告 §3.2 与 `gen-hazard.py` 的思路；`TeachingCpuObs` 作为比对的稳定接口。
- **做什么**：写一个限定在当前步骤指令集内的随机程序生成器，把学生核和参考核的 COMMIT 流逐条比对。
- **怎么算过**：连续 N 个随机程序零差异；人为植入一个核 bug 后差分在 M 个程序内抓到，并给出第一条分歧。

### V8 测试工具本身（随时）

- **学什么**：运行脚本、驱动程序、检查器会出错，而且它们的错误表现为"全绿"。实例：`TAIL_ERR` / `TAIL_DROP`
  是对**驱动程序**的测试，"一个看到值出现在内存就停的驱动会把这次运行判为通过"；本教学包的第一版
  `run-test.sh` 把位置参数后面的 `-P` 悄悄丢掉，三种时序跑出了同样的 93 拍；`build | tail` 隐藏构建状态；
  `a; b; c` 只报告 c 的结果。
- **读什么**：harness 的 `TAIL_*`；`teaching/tools/run-test.sh` 和日志第一行的 `PARAMS`；
  `tools/board/scripts/mem-preflight-selftest.sh` 的 19 个"缺证据就拒绝"用例。
- **做什么**：给 `run-test.sh` 注入一个缺陷（比如忽略 `--expect`），证明整套 `make step1-all` 仍然绿；
  然后写一个自测让它红。
- **怎么算过**：`make selftest` 存在，并且对脚本的每一个关键分支都有一个必须失败的输入。

### V9 证据与可复现（配合第 9、10 步之前）

- **学什么**：结果要能被别人重跑。身份哈希与清单（`verify_baseline_identity.py` 15 项冻结输入）；超时是结果
  不是通过；仿真与实板数据永不混合；测量策略在看到结果**之前**定下（`ROI-POLICY.md`）；"缺少证据是拒绝，
  不是默认值"。
- **读什么**：`experiments/IPS-campaign/CAMPAIGN.md` 的测量契约；`benchmarks/INSTRUMENTATION-CONTRACT.md`；
  `docs/TEACHING-PLAN.md` §4 的身份表。
- **做什么**：为自己的第 1 步核产出一个证据包：源码哈希、工具版本、全部日志、PARAMS、判定；再写一个检查器，
  对缺任何一项的证据包拒绝。
- **怎么算过**：换一台机器按证据包重跑得到同样的 COMMIT 流；删掉证据包的任一文件，检查器拒绝并说出缺什么。

两条轨道用同一个 harness、同一份学生核。测试轨道的产出（新监视规则、生成器、检查器）回到 `teaching/` 里，
成为实现轨道后续步骤的验收设施。所以这个分支的定位是开发测试轨道的材料，成熟一块就合回 `teach-rv64ia`，
不是长期分叉。
