# 第 4 步：中断

目标：核接受三根外部中断线（软件 MSI、定时器 MTI、外部 MEI），在**架构边界**上、而且只在架构边界上接受它们，
记录现场、进处理程序、`mret` 回到那条还没执行的指令。做完这一步，MCU-0 的闪灯固件可以从轮询改成 `wfi` 睡眠加定时器中断。

唯一的新机制：**中断只在 S_IF_REQ 采样。** 那一拍前一条指令的所有写入已经在 S_ARCH 落地，下一条指令还没有向总线发出任何东西，
所以没有任何东西需要取消或重做，`mepc` 就是 `pc`。

## 这一步在哪

| | |
| --- | --- |
| 前面 | 第 1 步取指和写回，第 2 步 RV64I，第 3 步异常、M 模式 CSR、`mret`。中断复用第 3 步的整条 trap 路径 |
| 这一步 | 中断只是"另一种进 trap 的原因"：多两个 CSR（`mie`、`mip`），多一个判定点（S_IF_REQ），多一条指令（`wfi`） |
| 后面 | 第 5 步把 CLINT、HTIF 做成仿真里的真设备，中断线由真的 `mtime >= mtimecmp` 拉高；第 6 步加 S/U 模式和中断委托 |

**这一步不涉及**（遇到了可以先不管）：

- `wfi` 真的睡眠：这里它是合法的空操作，规范允许。真正停止取指、等 `mip & mie` 的实现留作扩展。
- 向量模式的 `mtvec`（MODE = 1）：所有 trap 都进同一个入口，由处理程序看 `mcause`。
- 中断嵌套：进 trap 时 MIE 清零，处理程序里不会再被打断。
- 中断源本身：测试里由 harness 的注入器拉高中断线，不需要你写 CLINT。
- S 模式的中断位（SSIP/STIP/SEIP）、`mideleg`：第 6 步。

## 开始之前

```sh
make step3            # 必须全过：第 4 步建立在第 3 步的 trap 路径上
make step4            # 第一个失败会是 i01 超时：mie 还是未知地址，`csrw mie` 触发非法指令
```

`make step4` 遇到第一个失败就停。做到一半想看全部结果时用 `make -i step4`。

## 做什么

| 组 | 内容 |
| --- | --- |
| CSR | `mie`（0x304）：bit 3 MSIE、bit 7 MTIE、bit 11 MEIE 可写，其余读 0。`mip`（0x344）：同样三位，直接反映三根中断线的电平；**写 `mip` 合法但不改变任何东西** |
| 判定 | 挂起 = `mip & mie`；可接受 = `mstatus.MIE && 挂起非零`；优先级 MEI > MSI > MTI |
| 接受 | 在 S_IF_REQ，**先于**取指地址检查：cause = `{1, 0…, 11/3/7}`，tval = 0，epc = `pc`，`trap_interrupt` = 1，进 S_TRAP，不发取指请求 |
| `wfi` | 0x10500073，合法的空操作，退休一次。不睡眠，也不会让一个被屏蔽的中断变得可接受 |
| 观测 | `dbg_irq_enabled`、`dbg_redirect` 两根观测线必须实现，注入器靠它们定位（见 TODO 6） |
| 变异开关 | `EARLY_IRQ`、`STALE_MIE`、`IRQ_BAD_MEPC`，见下 |

## 中断从哪来

harness 有一个测试用的"中断控制器"：一个注入器在你指定的**微架构时刻**拉高某根线（`IRQ_POINT`、`IRQ_LINE`），线一直保持高，
直到处理程序往 `0x6000_0000` 写一次把它安静下来。核里没有任何"粘住的挂起位"：电平就是挂起。共享处理程序
`tests/cpu/tests2/ihandler.S` 负责记录 cause、计数、安静中断源。测试程序可以往 `0x6000_0008` 写 1 来**布防**：
之后的下一次指定时刻才注入，避免启动代码抢走那一次。

| `IRQ_POINT` | 时刻 | 核此时的状态 |
| --- | --- | --- |
| 1 | 取指请求挂着、ready 还没来 | S_IF_WAIT |
| 2 | 取指已握手、响应还没回来 | S_IF_WAIT |
| 3 | 数据请求挂着、ready 还没来 | S_MEM_WAIT |
| 4 | 数据已握手、响应还没回来 | S_MEM_WAIT |
| 5 | 写回调度的那一拍 | S_WB |
| 6 | 一条跳转、分支或 mret 正在写回 | S_WB，`dbg_redirect` 为 1 |
| 7 | 写入落地的那一拍 | S_ARCH |

无论注入在哪个时刻，正确的核都只在下一次 S_IF_REQ 接受它；在途的取指、访存都正常完成，那条指令照常退休。

## 测试

```sh
make step4            # 20 次运行
make step4-mutants    # 5 个检查
```

| 测试 | 查什么 |
| --- | --- |
| i01 ×2 | 一个定时器中断：cause 带中断位，返回后 `mip` 为 0，不再有第二个；另跑一次随机时序 |
| i02 | 三根线同时拉高，接受顺序必须是外部、软件、定时器 |
| i03 | `mstatus.MIE` 关、或 `mie` 关时，一直挂着的电平都不能被接受；打开后立刻接受 |
| i04 | `mip` 只是电平的窗口：写它合法，但既不能凭空产生、也不能清掉挂起位（第 4 步版本，`-DHAS_S` 时期望不同） |
| i05 | `wfi` 退休恰好一次，使能关时只是继续往下执行 |
| i06 | `mret` 恢复使能时中断源还挂着，必须立刻再次进入，三次，`mepc` 都相同 |
| i07 | 在一条被采纳的回跳分支写回时注入：`mepc` 必须是**跳转目标** |
| i08 | 中断注入在一条会出总线错误的 load 的响应期间：load 的访问错误先报，中断其后 |
| i09 ×3 | 中断落在 store 的请求期、响应期、慢总线：读回的值正确，恰好一次中断 |
| j01 ×6 | 使能确认生效后布防，中断分别落在目标 load 的六个时刻；load 完成并退休，`mepc` 恰好是下一条 |
| j02 ×2 | 50 次读加写同一地址，**在总线上计数**：req 102、写请求 51、实际写入 51；快总线和慢总线各一次 |

每次运行除了程序自己的检查，还核对日志里的注入上下文：时刻真的出现过（`hits > 0`）、线拉高一次、被安静的次数、
触发时的状态和 pc（`fire_pc=@target_insn@` 这种写法会被换成标签的实际地址）、使能是否真的生效。
**一个只看"中断最后被处理了"的测试，会让在错误时刻接受中断的核蒙混过关。**

## 杀死矩阵

| 变异体 | 含义 | 被谁杀死 |
| --- | --- | --- |
| `STALE_MIE` | 在 S_ARCH 就采样，用的是还没落地的 MIE | 除 i04 外全部。进 trap 时 MIE 的清零还没落地，同一个中断在处理程序第一条指令前再进一次，`mepc` 被覆盖成处理程序地址（i01 日志里两个中断只隔 2 拍，第二个的 epc 是 `trap_handler`，判定就看这一行）。之后怎么坏取决于核：只有 M 模式的核在处理程序里绕圈直到超时；参考核的 `mret` 会落到 U 模式，一路非法指令 |
| `IRQ_BAD_MEPC` | 中断的 `mepc` 记成上一条指令 | i07、i08、j01 六个时刻 |
| `EARLY_IRQ` | 也在 S_MEM_WAIT 接受，放弃已经发出的访存 | j01 取指和访存请求期（撤回请求、`mepc` 错）；**j02 慢总线**（store 被执行两次） |
| `DUP_STORE`（harness 的对照） | 内存模型把一个被监视的写执行两次 | 只有 j02 的 `writes` 计数 |

`EARLY_IRQ` 在 i09 里**活了下来**：store 被中断吞掉后，处理程序返回到它，它又执行一遍，写的是同一个值，程序看不出来。
只有在总线上数请求和实际写入的 j02 能抓住它。这是这一步最值得记住的一课：**"最终值对"不等于"恰好一次"。**

判定为接受时不能发出取指请求。

## 为什么可以相信这些测试

- 参考核（`CORE=../rtl/cpu`）20 次运行全过，所以测试本身没有写错期望。
- 每个变异体都按杀死矩阵里写的原因失败（`--grep` 核对的是失败码或日志行，不只是"失败了"），所以测试真的能抓住这几类错。
- `DUP_STORE` 是 bench 给自己做的对照：故意让内存把一个写执行两次，j02 的 `writes` 计数必须跟着变。它证明总线计数本身是可靠的。
- 每次运行都核对注入上下文（时刻、状态、pc、使能），所以"中断最后被处理了"不足以通过。

测试失败时，先怀疑自己的核。参考核上同样的命令能过，就说明问题在你这边。

## 自测问题

做完以后不看代码回答。答不上来的，回到对应的 TODO 再看一遍。

<details><summary>1. 为什么中断只在 S_IF_REQ 采样，而不在 S_MEM_WAIT？</summary>

S_IF_REQ 时上一条指令已经完全落地，下一条还没向总线发出任何东西，没有需要取消的事情。S_MEM_WAIT 时访存已经发出，
放弃它就要重做：j02 慢总线上 store 会被执行两次（`EARLY_IRQ`）。
</details>

<details><summary>2. 中断的 mepc 为什么是 pc，而同步异常的 mepc 也是 pc，两者意思一样吗？</summary>

不一样。同步异常的 pc 是**出错的那条**指令，处理程序通常跳过它或修好它再重做；中断的 pc 是**还没执行的那条**指令，
返回后从它开始执行。如果它前面是一条跳转，pc 已经是跳转目标（i07）。
</details>

<details><summary>3. 为什么 trap 必须经过 S_ARCH，不能从 S_TRAP 直接回 S_IF_REQ？</summary>

trap 清 MIE 的写入要在下一次 S_IF_REQ 判定之前落地。直接回去，判定看到的还是旧的 MIE=1，同一个中断被接受两次（`STALE_MIE`）。
</details>

<details><summary>4. 写 mip 为什么合法却不起作用？那中断源怎么清？</summary>

0x344 的 [11:10] 不是 11，所以写它不是非法指令。但 MSIP/MTIP/MEIP 是外部电平，核里不存它们。要清就得找源头：
写中断控制器（测试里是 0x6000_0000，真实系统里是 CLINT 的 msip、mtimecmp）。
</details>

<details><summary>5. i09 为什么抓不住 EARLY_IRQ，j02 为什么能？</summary>

被吞掉的 store 返回后又执行一遍，写的是同一个值，程序读回来看不出差别。j02 在总线上数实际写入次数，51 变成 52 就暴露了。
"最终值对"不等于"恰好一次"。
</details>

<details><summary>6. wfi 实现成空操作，为什么不算偷懒？软件要怎么写才对？</summary>

规范允许 `wfi` 随时返回。所以正确的软件总是把它放在检查条件的循环里：`while (!flag) wfi();`。
空操作的 `wfi` 只是让这个循环变成忙等，结果仍然正确。
</details>

## 做完能玩什么

MCU-0 的顶层已经把 CLINT 的 `mtip`、`msip` 接到了核的中断输入上（`mcu_top.v`），所以下面这些**只换固件、不改硬件**：

- **定时器中断闪灯**：设好 `mtimecmp`，主循环里 `wfi`，处理程序翻转 LED 并把 `mtimecmp` 往后推。和第 3 步的轮询版对比代码结构。
- **两个任务的抢占式轮转**：定时器中断里保存一套寄存器、换另一套、`mret`。两个任务各自闪一个 LED，谁也不用主动让出。
  这是最小的"操作系统内核"。
- **固定节拍采样**：步进电机或按键扫描放进定时器中断，节拍不再受主循环里其他工作的影响。
- **软件中断**：写 CLINT 的 `msip` 给自己发一个中断，把耗时的工作推迟到处理程序之外。

一个小的硬件练习：MCU-0 的 `irq_meip` 现在接的是 0。给 GPIO 加一个"按键变化"信号接到 `meip`，按键就能直接触发中断。

**还做不到**（后面的步骤解决）：

- 真正省电：`wfi` 还是忙等。
- 很多个中断源：只有三根线，外设多了要中断控制器（PLIC）。
- 保护：所有代码都在 M 模式，一个任务能改掉另一个任务的内存和 CSR（第 6 步 S/U 模式、第 7 步 Sv39）。
